## 2026-07-24 -- a "confirmed via selftest" claim can be measuring the WRONG config entirely: ES module import hoisting silently defeats a late-placed process.loadEnvFile() call
Goal (G): After 100+ prior sessions each declared casey's LLM-reliability problem fixed and it recurred anyway, run a genuinely adversarial, repeated verification before making any claim, and find the actual structural gap rather than another point patch.
What drifted / what went wrong: earlier this session, bin/selftest.js was fixed to call process.loadEnvFile() so it would pick up .env-tuned settings (chain cap, turn deadlines) instead of running on code defaults. That fix was itself broken and went undetected for several more fix-verify cycles: ES module `import` statements are hoisted -- they evaluate before ANY top-level code in the importing module, so a loadEnvFile() call placed as the literal first statement after the imports still runs AFTER every statically-imported module (casey.js, transitively hooks/handler.js) has already captured its own module-level `const X = Number(process.env.Y) || default` constants from an incomplete process.env. This meant a 3-run adversarial selftest audit (run specifically to get real, repeated evidence before reporting anything) was silently measuring the STALE 60000ms deadline the whole time, not the 90000/120000 the .env had actually been tuned to -- directly caught because every failing run degraded at exactly ~60406ms regardless of what .env said. Worse: the SAME bug existed in bin/casey.js, the actual production entry point `casey up` runs -- meaning the live production worker had likely never honored ANY of these .env-tuned constants either, across this entire session and probably many prior ones. This affected not just the one deadline being tested but every module-level env-derived constant in hooks/handler.js, hooks/media.js, and supervisor.js at once (7+ settings).
Fix / resolution: a bootstrap-entry-point pattern for both affected files -- a new file with NO static imports of its own that calls process.loadEnvFile() first, then `await import('./real-module.js')` to hand off. Dynamic import() only begins evaluating its target after the import() line actually runs, so hoisting cannot skip ahead of it. bin/selftest.js's real logic stayed in place, driven via a new bin/selftest-bootstrap.mjs; bin/casey.js's ~750-line CLI implementation was moved verbatim to bin/casey-cli.mjs, with bin/casey.js rewritten as the minimal bootstrap (preserving the npm bin entry and every documented `node bin/casey.js <cmd>` invocation). Re-ran the full adversarial suite through the corrected bootstrap and got materially different (much faster, more consistent) results than the pre-fix runs.
Generalizes to: (1) In ANY ES module (`"type": "module"` / `.mjs`) codebase, a `process.loadEnvFile()`/dotenv-style call is NEVER safe to place in the same file as the imports it's meant to precede -- it must live in a separate bootstrap file with zero static imports of its own, dynamically importing the real entry point after the env load completes. A late-placed env load in the SAME file will pass a casual read (the code visually appears before the logic that needs it) while being functionally too late for every module-level constant the import graph already evaluated. (2) Any CLI/entry-point script bearing a comment like "load .env so X doesn't need to be exported" is worth directly re-verifying against a module-level constant's actual captured value, not just checking that the loadEnvFile() call exists and doesn't throw -- existence of the call is not proof it runs early enough. (3) When a fix is verified via a test harness, always ask whether the harness ITSELF could be silently measuring stale state (a cache, a hoisting-order bug, a config file it isn't actually reading) before trusting a "confirmed" result -- this exact class of self-referential harness bug is what let a real config change go unverified through multiple rounds of "should be fixed now" claims.
