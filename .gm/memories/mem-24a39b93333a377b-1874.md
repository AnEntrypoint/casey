casey dashboard middleware order is load-bearing. The error middleware is registered LAST because express only routes an error to middleware defined after the throwing point; it never echoes err.message or a stack (casey never sets NODE_ENV=production, so the framework default would leak a stack trace and filesystem paths to anonymous clients). The WhatsApp webhook is registered FIRST: express matches in order, so that is what keeps it clear of compressResponses, express.json (which would consume the raw bytes the HMAC is computed over), the session middleware, the CSRF guard and authGate; it is not unauthenticated, it carries Meta's X-Hub-Signature-256. compressResponses is hand-rolled over node:zlib (no dependency casey can write in a few lines): it compresses status 200 only (206 range offsets must stay meaningful, 304 has no body), skips sub-kilobyte bodies, always sets Vary even when this response is not compressed (a shared cache must not hand gzip to a client that did not ask), deletes Content-Length (it describes the original body and would truncate the response), and streams rather than buffering so the CSV export keeps streaming. CASEY_TRUST_PROXY_HOPS must be set to the real number of proxy hops when casey is behind a reverse proxy: unset, every request's peer is the proxy and reportRateLimited keys ALL farmers into one 10-per-60s bucket; set too high, a client can spoof X-Forwarded-For to bypass the limiter. CSV export neutralises a leading = + - @ so contact-supplied text never runs as a formula (CWE-1236) and quotes a bare carriage return, which splits a row in Excel and many parsers. /tiles stays behind the auth gate because an ungated tile route is an open proxy onto openstreetmap.org; it never serves blank tiles and keeps the User-Agent, Referer, 7-day freshness floor, zoom cap and no-prefetch rules from the OSM usage policy.
