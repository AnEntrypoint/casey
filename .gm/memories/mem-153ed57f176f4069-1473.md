casey backup.js rules. A raw-copy fallback must include the -wal and -shm sidecars: copying db.sqlite alone while a -wal file exists is the classic silently-corrupt backup, because the committed transactions living in the WAL are absent from the copy. The snapshot path checkpoints everything into the single file. Restore removes any stale sidecar beside the restored database, because sqlite would replay the OLD write-ahead log over the restored file on next open; any sidecar present at that point belongs to the database that was just moved aside. A non-empty target directory is refused rather than merged, because a half-overwritten backup is worse than none: it looks complete. Restore is destructive by construction, so it needs a readable manifest and an explicit confirmation, and the live data directory is MOVED aside, never overwritten, so a restore from the wrong backup is itself recoverable. The freddie session transcripts are copied whole, keyed by the project segment freddie uses, so a restore puts them where run-turn.js finds them; an absent transcript root is reported missing, not failed. Everything else under data/ is discovered rather than listed, and db.sqlite plus its sidecars are skipped there because copying them again would overwrite the consistent snapshot with an inconsistent one. The manifest is written into the artifact, not only printed, because whoever reads the directory during an incident is not the person who ran the command.
